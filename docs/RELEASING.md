# Release runbook

The GitHub repository was made public by the owner before the first release. `main.js` is a generated release asset, not tracked source. Never change it manually for a permanent fix. Node 22+ is required for development; `minAppVersion: 1.5.0` is inherited and has **not** been tested on that exact Obsidian version. The owner chose to retain it and accepts that directory review may ask for a justified minimum. No public historical releases were found at preparation time; `versions.json` now retains the actual published 1.0.4 and 1.0.5 mappings.

1. Work on a release branch while the default branch still serves the last **published** manifest version (for the first release, coordinate default branch visibility and submission). Update with `npm run version:sync -- x.y.z` only after checking that the version/tag does not exist. Review the metadata and `git diff`. Run `npm ci`, `npm run check`, `npm run package`, `RELEASE_TAG=x.y.z npm run release:check`.
2. Record [manual tests](MANUAL-TESTS.md), including real Android, desktop modes and the minimum Obsidian version where available. For 1.0.4 the owner reported successful basic desktop and Android smoke tests and accepted unverified specialized cases and minimum-version compatibility. Update `docs/RELEASE-NOTES.md` for the exact version. Review `dist/main.js`, separate assets, ZIP, `SHA256SUMS` and release notes. Fix failures in source and rebuild; never edit built assets in isolation.
3. Owner: commit and push reviewed release branch, then create and push an exact `x.y.z` tag (no `v`) from the reviewed commit. The **Release draft** GitHub Actions workflow is manual: Actions → Release draft → Run workflow → enter existing tag. It checks out that tag, runs all checks and creates a **draft** with `main.js`, `manifest.json`, `styles.css`, ZIP and SHA256SUMS. Existing releases, including drafts, cause the job to fail without overwriting assets; investigate a collision manually, never use `--clobber` on a published release. No PAT is required.
4. Compare downloaded draft assets and checksums; when appropriate, install in a separate test vault, smoke test and inspect release notes. Publish the reviewed draft from GitHub's release UI (or `gh release edit x.y.z --draft=false`). For 1.0.4 the owner explicitly authorized publishing after CI and asset verification on the basis of their reported local desktop/Android smoke tests. A draft/prerelease is not a public Community Plugins release. Align the public default-branch manifest with the released version and verify assets download without authentication; minimize any interval where a public default branch points to an unavailable draft.
5. For first submission follow [COMMUNITY-SUBMISSION.md](COMMUNITY-SUBMISSION.md). Directory acceptance is separate from CI. Review fixes require a **new version and new release**, not replacing published assets. Never submit on behalf of the owner.

`release:check` verifies exact metadata/asset bytes, ZIP layout and checksums, but does not prove native device compatibility, external catalogue uniqueness or public reachability.
